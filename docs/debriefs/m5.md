# Builder's Debrief — M5: Our model in the app (ONNX serving next to PANNs)

> Branch `m5`. Plan line (ML_ENGINEERING §8): "ONNX serving swap in the app; draft-2 report
> shows leaf-level instruments". Served model: `scratch_cnn_synthetic_v7s` (the M4 v7
> recipe re-rendered with no held-out sources: 10k clips, 1.22M params, best synthetic val
> mAP 0.886). It lives at `~/.disstruments/models/leaf`, outside the repo, because its
> licence is research-only (§6). `make leaf-model` rebuilds it.

## What shipped

- **Stage B2 `tagging_leaf`.** It runs our CNN over the full mix, using non-overlapping
  10 s windows from t = 0 (the same windows as the pooled MoisesDB eval). Features come
  from `scratch.logmel_array`, which the training mel cache uses too, so training and
  serving features can't drift. A test enforces bit-for-bit equality.
- **ONNX export and sidecar** (`ml/models/export.py`, `disstruments.leafmodel/v1`). The
  sidecar records:
  - sha256 (checked on load, F13), taxonomy version and sha, trained nodes, features;
  - one global temperature fit on OpenMIC train (real, never trained on): T = 2.013, NLL
    0.539 → 0.458, n = 14,915;
  - `leaf_calibrated: false`, the routing, the licence and the NSynth attribution.
- **Fallback.** With no model on disk the stage is recorded as `skipped` and the report is
  PANNs-only.
- **Report schema v2.** Every instrument entry carries `node`, `model` and `calibrated`.
  Subtype entries carry `subtype: true`, and the UI always shows them with "?".
  `provenance.leaf_model` names the model, its version, sha, T, licence and routing.
- **Library filter.** Rows are now keyed by taxonomy node, and filtering on a family
  matches its whole subtree (filtering "guitar" finds nylon guitars).
- **Tests.** 467 pass (fake-ML mode). That count includes:
  - ONNX vs torch parity;
  - serving max-propagation;
  - p95 aggregation;
  - every routing rule.

## Routing: who decides what (chosen from measurements)

Both comparisons use paired artist bootstraps, are scored by AP, and pit the serving model
(v7s) against **raw, mix-only** PANNs, which is how the app ran PANNs when routing was
decided. See the bass re-check below.

| node | MoisesDB pooled (720 × 10 s) | OpenMIC test |
|---|---|---|
| guitar | +0.00 [−0.06, +0.05] | −0.04 [−0.07, −0.02] |
| **bass** | **+0.18 [+0.13, +0.24]** | −0.02 [−0.13, +0.08] |
| keys / piano | +0.00 / −0.08 [−0.16, −0.02] | piano +0.00 |
| drums | +0.01 [−0.00, +0.03] | −0.04 [−0.08, −0.00] |
| voice | −0.56 (never trained on voice) | −0.52 |

- **Presence rule:** our model owns presence only where it beats the incumbent on real
  music and is never worse.
  - Against raw mix-only PANNs, that was **bass** (+0.18).
  - **Re-checked against the incumbent the app now runs** (calibrated PANNs, mix + bass
    stem; stories 4 and 8): bass AP is 0.982 vs 0.978, a difference of +0.004
    [−0.008, +0.020]. **That's a tie, so presence went back to PANNs** (`PRESENCE = []`).
  - The +0.18 was mostly the bass *stem* that the harness never scored. This is a third
    case of "the eval isn't what the app runs".
  - Our model now only names subtypes, under PANNs' instruments. Ours does have higher
    recall@0.6 on bass (0.72 vs 0.65), but the rule is about ranking, and changing it to
    keep a win would be post-hoc.
- **Subtype rule:** under a present instrument, our model may name a subtype. A subtype
  is suppressed when its normalized AP lift (AP − base)/(1 − base) on pooled MoisesDB
  is below 0.1, or when it is flat on unseen instruments.

| subtype (MoisesDB pooled) | v7 lift | **v7s lift (served)** | decision |
|---|---|---|---|
| guitar.acoustic / .electric | +0.33 / +0.47 | +0.40 / +0.49 | shown |
| guitar.electric.clean / .distorted | +0.15 / +0.71 | +0.18 / +0.67 | shown |
| bass.electric / .upright / .synth | +0.84 / +0.14 / +0.20 | +0.81 / +0.11 / +0.15 | shown |
| keys.electric_piano | +0.06 | +0.09 | **suppressed** |
| keys.synth.pad | +0.01 | +0.06 | **suppressed** |
| keys.synth.lead | +0.15 | +0.18 | shown |
| drums.acoustic_kit / .electronic | +0.94 / +0.38 | +0.94 / +0.56 | shown |
| bass.electric.fingered / .picked | – | – | **suppressed** (flat on unseen basses, M4) |

**Routing was re-checked on the served model.** The rules were chosen on v7, the model
that held out unseen sources. Every decision held on v7s.

## Serving checks

- **ONNX vs torch:** max |Δp| 2.9e-6 on 64 real mels.
- **App vs eval harness:** I ran 5 MoisesDB songs, 3 consecutive windows each, through
  the app's real decode → resample → window → ONNX path. The worst gap from the
  harness's scores was 2.8e-4.
- **Latency on an idle M5 CPU:** a 180 s song takes 0.40 s end to end (inference 0.25 s;
  torch-MPS 0.07 s). In the app, a 133 s song took 0.33 s. The budget is 15 s.
- **Real app run:** `uvicorn` with real models on an isolated data dir, uploading a CC
  song (*Let's Go Fishin'*, librosa example). Every stage finished OK.

## Bug and failure stories

**1. The app scored parents differently from the eval** (caught by review before shipping).
- **What happened:** the harness max-propagates scores (parent = max(self, descendants)),
  but serving used raw parent outputs. On `bass` the two differed by up to 0.5. So no
  number I had measured described what the app actually did.
- **Fix:** serving applies the same `max_propagate`. Global T is monotone, so it commutes
  with the max. Calibration is fit on propagated scores, and a test pins the behaviour.

**2. Seven lanes for one song.**
- **What happened:** the first real run listed all 4 guitar subtypes and 3 bass subtypes,
  each with "?". An absolute 0.3 cut-off on *uncalibrated* leaf scores lets every sibling
  through. "Distorted" scored 0.53 on an acoustic song.
- **Fix:** one lane per instrument. Starting at the family node, step down only while the
  best trained child beats its runner-up by **0.2** (`leaf_tagging.descend`).
  - It compares siblings because one global T can't change how siblings rank, but it does
    shift absolute leaf scores.
  - Suppressed and unlisted children still compete, but are never named.
  - A node with one trained child is never descended. TR-808 is the only trained drum
    machine, so naming it would be meaningless.
- **On choosing the margin:** I fixed 0.2 before the re-run and didn't tune it. I had
  already seen this song's raw scores, so this song isn't evidence for the margin; the
  golden set is.
- **Result:** the song now shows one bass lane and one guitar lane. Which subtype it names
  turned out to be level noise (story 5).

**3. Subtypes on the wrong stem.**
- **What happened:** subtype entries inherited the stem PANNs found the family on. PANNs
  heard this song's guitar bleeding into the *bass* stem, so "Nylon-string guitar" pointed
  the mixer at the bass stem. Our scores come from the mix.
- **Fix:** every entry from our model is `stem: "mix"`. The end-to-end test asserts it.

**4. Good AP, while hiding nearly everything users see (the headline finding).**
- **The gap:** the routing compared models by AP, which ignores thresholds. The app shows
  instruments at fixed thresholds (F15: hidden below 0.30, "?" from 0.30 to 0.60). At
  those thresholds PANNs recovers almost nothing:

  | MoisesDB pooled | PANNs recall@0.3 | PANNs recall@0.6 | ours recall@0.3 (precision) | ours recall@0.6 |
  |---|---|---|---|---|
  | voice (268) | 0.06 | 0.00 | – (untrained) | – |
  | drums (514) | 0.05 | 0.02 | 0.99 (0.89) | 0.96 |
  | guitar (512) | 0.13 | 0.01 | 0.99 (0.82) | 0.78 |
  | bass (514) | 0.01 | 0.00 | 0.98 (0.84) | 0.72 |
  | keys (394) | 0.04 | 0.00 | 0.99 (0.59) | 0.53 |

  "Ours" means the app's numbers: the harness scores with the served T = 2.013 applied
  (see story 7). On OpenMIC test it's less extreme but the same story: PANNs drums
  recall@0.3 / @0.6 is 0.47 / 0.23 vs ours 0.99 / 0.96; PANNs voice is 0.19 / 0.03.
- **What it means:** PANNs ranks well (voice AP 0.99) but its raw scores sit far below
  0.3. This is the phase-1 "no voice, no drums" finding, now measured on 720 real windows
  rather than one song. Our model's scores are usable at these thresholds. The T fit on
  OpenMIC trades a little precision for recall; keys precision is the weak spot at 0.59.
- **Lesson:** the routing metric has to include the operating point users actually see,
  not only a threshold-free ranking metric.
- **Caveat (resolved in story 8):** the harness scores PANNs on the mix only, but the app
  also tags 4 Demucs stems. Story 8 measures what the app actually does.
- **Fix (Bradley approved): per-class Platt scaling for PANNs.**
  - The map is p' = sigmoid(a·logit(p) + b), fit on PANNs' OpenMIC-train scores (14,915
    clips, real, never trained on). The bias matters: the fitted b is +4 to +7 for
    voice, drums, guitar, piano and synth, which no temperature could produce.
  - It's applied framewise in `tagging.tag`, so activation regions move too.
  - Provenance reads `cnn14+platt@<sha>`, and `DISS_PANNS_CALIBRATED=0` restores raw
    scores.
  - It's monotone, so AP is unchanged and so is every routing decision.

  | pooled MoisesDB (independent of the fit), mix | raw recall@0.3 | calibrated recall@0.3 (precision) | calibrated recall@0.6 | ECE raw → cal |
  |---|---|---|---|---|
  | voice | 0.06 | **0.96 (0.98)** | 0.85 | 0.56 → 0.11 |
  | drums | 0.05 | **0.83 (0.97)** | 0.62 | 0.74 → 0.26 |
  | guitar | 0.13 | **0.82 (0.90)** | 0.54 | 0.71 → 0.26 |
  | piano | 0.06 | 0.31 (0.70) | 0.21 | 0.32 → 0.21 |

  On OpenMIC test (the fit's own source) ECE falls to 0.02–0.07 for every class. On
  MoisesDB, calibrated PANNs is still *under*-confident on drums and guitar (ECE 0.26), but
  precision stays at 0.90 or above. The OpenMIC base rates didn't flood real songs with
  false positives.

**5. The model depends on input level.**
- **What happened:** on the same song, nylon vs steel was 0.88 vs 0.83 on the original
  file but 0.89 vs 0.64 after the app's transcode. The waveforms correlate at 0.99994; the
  transcoded audio is just **3 dB quieter**. ffmpeg's mono→stereo upmix (`-ac 2`) applies
  a −3 dB pan law, and our mean-downmix keeps it.
- **Measured on pooled MoisesDB:** AP rises steadily with gain.

  | node | −6 dB | −3 dB | as-is | +3 dB |
  |---|---|---|---|---|
  | guitar.electric.distorted | 0.635 | 0.693 | 0.756 | 0.789 |
  | guitar.acoustic | 0.563 | 0.596 | 0.632 | 0.676 |
  | keys | 0.703 | 0.735 | 0.778 | 0.808 |
  | drums.electronic | 0.511 | 0.570 | 0.599 | 0.625 |

  Window scores move about 0.04 per 3 dB.
- **Cause:** the renders are loudness-normalised, features are `log1p(100·mel)` (not
  level-invariant), and training only uses SpecAugment, with no gain augmentation.
- **What it did to the test song:** the −3 dB flipped *both* lanes of the post-fix run.
  - Bass: on the original file, electric (0.81) beat synth (0.57) by 0.24, so the lane
    would say "Electric bass". After transcode it's 0.77 vs 0.57, a margin of 0.19, so the
    lane says "Bass (subtype uncertain)".
  - Guitar: nylon vs steel goes from 0.88 vs 0.83 (stop at "Acoustic guitar") to 0.89 vs
    0.64 ("Nylon").

  So the post-fix run shows the rule working mechanically, but its specific nylon call is
  level noise, not evidence.
- **The −3 dB reaches PANNs too:** it averages channels the same way (`librosa.load`). That
  gives phase-1's "22 kHz mono confound" a concrete mechanism. It isn't the main cause of
  story 4: MoisesDB clips are stereo, and PANNs recall is still about 5% there.
- **Fix (next model):** random gain augmentation in the mel cache, or per-window level
  normalisation in both training and serving, then re-evaluate. Separately, upmix mono
  uploads without the pan law.

**6. My own analysis bug.** In the threshold comparison I first indexed the full-taxonomy
label matrix with PANNs' 27-node list. Bass showed 249 positives instead of 514, which is
how I caught it. Rerun correctly before anything was written down.

**7. My threshold table first left out the temperature** (caught by review). The harness
archives *uncalibrated* scores (T = 1). The app divides logits by T = 2.013, which pushes
scores toward 0.5, so recall at 0.3 goes up and precision goes down. The table above is
the corrected, T-applied version. It's the same kind of slip as story 1: an eval number
that isn't what the app computes.

**8. Calibration made the stems invent instruments.**
- **What happened:** after calibration the test song showed voice (0.95) and drums (0.97),
  but also synth 0.92 (bass stem), ukulele 0.87 (vocals stem), banjo 0.81 and mandolin
  0.58 ("other" stem).
- **Cause:** the app took each label's max over the mix and all 4 stems. Raw PANNs
  scores were too low for that to matter. Calibrated, five inputs mean five chances to
  fire, and the stems are out of distribution for a fit made on mixes.
- **Measured the app's real path:** canonical transcode → htdemucs → PANNs on all 720
  pooled-MoisesDB windows (~40 min on MPS). False detections at 0.3, across 10,606
  labelled negatives:

  | rule | false shows | voice R/P@0.3 | drums R/P@0.3 | bass R/P@0.3 | guitar R/P@0.3 |
  |---|---|---|---|---|---|
  | mix only | 448 | 0.96 / 0.98 | 0.82 / 0.97 | 0.42 / 0.77 | 0.82 / 0.90 |
  | mix + all stems (the old rule) | **2238** | 1.00 / 0.92 | 1.00 / 0.93 | 0.95 / 0.87 | 0.97 / 0.85 |
  | **mix + dedicated stem (shipped)** | **471** | 1.00 / 0.96 | 0.99 / 0.96 | 0.94 / 0.88 | 0.82 / 0.90 |

  The residual "other" stem was the main source: it "found" cello in 39% of windows and
  violin in 35%, though MoisesDB has neither.
- **Rule (`tagging.STEM_ROLES`):** a stem vouches only for the instrument Demucs separated
  it *for* (vocals → voice, drums → drums/cymbals, bass → bass). Everything else comes
  from the mix.
- **Cost:** piano recall 0.75 → 0.31, and guitar loses the other-stem boost.
- **Result:** *Fishin'* now shows drum kit, voice, bass, cymbals, a guitar lane, and
  "banjo ?" at 0.42, probably wrong but honestly marked uncertain.

## Follow-ups without the golden set (2026-10-12)

**F1. Mono uploads lost 3 dB.** Fixed: `to_canonical` copies a mono source to both
channels at unity gain. A test checks that the level is preserved, and the old code fails
it at −3.01 dB.

**F2. Gain-augmented retrain (story 5).** It's the v7s recipe and seed plus a random input
gain of ±12 dB per clip, applied exactly on cached features. **Adoption rule, written
before the results:** the gain model replaces v7s only if both hold:
1. on pooled MoisesDB, AP doesn't get worse beyond run-to-run noise (paired artist
   bootstrap CI not entirely below −0.01) on the coarse nodes or the served subtype nodes;
2. the −6 dB vs 0 dB AP drop clearly shrinks, measured with the same level-sensitivity
   script.

If adopted, the swap re-runs the export, subtype lifts and suppression, serving parity and
the test song.

**Result: adopted (served model now `scratch_cnn_synthetic_v7sg`, sha 0a1df16e1827).**
- **Condition 1 (real music no worse): passed, and it's a broad gain.** On pooled
  MoisesDB, mean leaf AP went from 0.408 to 0.490. Paired artist bootstrap vs v7s:

  | node | v7s → gain | Δ [95% CI] |
  |---|---|---|
  | keys.piano | 0.56 → 0.68 | +0.12 [+0.07, +0.18] |
  | guitar.electric.clean | 0.36 → 0.47 | +0.11 [+0.05, +0.17] |
  | guitar.electric | 0.74 → 0.82 | +0.08 [+0.03, +0.12] |
  | guitar.acoustic | 0.63 → 0.71 | +0.08 [+0.00, +0.17] |
  | guitar.electric.distorted | 0.76 → 0.82 | +0.06 [+0.02, +0.12] |
  | keys / keys.synth.pad | 0.78 → 0.84 / 0.19 → 0.27 | +0.06 / +0.08 (CIs > 0) |
  | bass.upright | 0.14 → 0.41 | +0.28 [−0.00, +0.48] |
  | drums.electronic | 0.60 → 0.52 | −0.08 [−0.18, +0.03] |

  OpenMIC test is flat (every class within ±0.03), as expected for loudness-consistent
  clips.
- **Condition 2 (level sensitivity shrinks): passed.** The mean AP drop from 0 dB to
  −6 dB over 15 nodes fell from 0.047 to 0.021. The new model at −6 dB beats v7s at +3 dB
  on most nodes. **The exception is guitar.acoustic,** whose −6 dB drop grew (0.068 →
  0.092).
- **What it means:** level was a real-music shortcut. The renders are loudness-normalised,
  so "louder → instrument present" was learnable and doesn't transfer. One cheap
  augmentation was worth more on real music than any M4 data lever.
- **Swap checklist:**
  - export: T = 2.034, ONNX parity 2.5e-6;
  - app vs harness: 4.4e-4;
  - the test song now shows "Electric bass" and "guitar (subtype uncertain)";
  - 477 tests pass.
- **Presence re-checked on v7sg** against the app-faithful PANNs (calibrated, plus the
  dedicated stem). Piano is the only node whose ranking moved enough to matter:
  - **piano:** +0.036 [−0.023, +0.114], a tie, so PANNs keeps it. At the user-facing
    threshold the two disagree: ours has recall@0.3 0.84 at precision 0.43, PANNs 0.31 at
    0.70;
  - **bass:** +0.006 [−0.008, +0.021], still a tie.
  - The check exposed a latent bug: owned presence only worked when the PANNs label was
    also a node name ("bass"). With "piano" the instrument would have vanished from
    reports. Fixed (label → node), with a test.
- **Routing re-applied mechanically:**
  - synth pad now passes (lift 0.15) and is listed under "synthesizer";
  - electric piano passes (0.13) but stays unreachable, because PANNs files e-pianos
    under "piano";
  - bass technique stays suppressed. On IDMT it's AP 0.34 vs a 0.25 base, and fingered
    fell from 0.51 (v7s) to 0.34 with only the augmentation changed, so it's unstable.

**F3. Whole-song scores: what p95 does (MoisesDB can't test it: only ~3 windows per song).**
The app's song confidence is the 95th percentile over 10 s windows (ours) or over ~0.3 s
frames (PANNs). For an instrument at full confidence in only part of the song:

| song length | heard in 1 window (10 s) | heard in 2 windows (20 s) |
|---|---|---|
| 1 min | 0.75 | 1.00 |
| 2 min | 0.45 | 1.00 |
| 3 min | **0.15** (hidden) | 1.00 |
| 4 min | **0.00** (hidden) | 0.85 |
| 5 min | 0.00 | 0.55 |

So the rule is effectively "audible for at least ~5% of the song". It's robust to brief
false positives, but it hides a short solo or intro instrument. **This is Bradley's product
call** (keep it, or switch to e.g. the mean of the top 20 s); the golden set can measure
it either way.

**F4. Licence-clean training data (PRD A2).**
- **Generator:** `ml/synth/procedural.py` writes seeded multi-track songs. Each has a drum
  kit groove, a bass line, chord parts (block / arpeggio / strum / offbeat), a melody and
  optional pad/horn lines, over common progressions, with tempo 72–164 and 40% minor keys.
- **Licence marker:** `MIDI_LICENSE.json` in the folder marks it owned; `build` reads it,
  so labels carry `commercial_clean: true` when every source is clean too.
- **Matched instrument mix:** part probabilities are tuned so role frequencies match the
  Lakh-based v7 render (guitar 0.78 vs ~0.85, piano/e-piano 0.60 vs ~0.60, pad 0.12 vs
  0.12, organ 0.13 vs 0.11). The licence ablation then differs in *composition*, not class
  frequency.
- **What `--commercial-only` drops:** exactly one source, jRhodes3d (CC BY-NC), 1,070
  Rhodes stems in v7, leaving 2 clean Rhodes sources. Rhodes sits under the suppressed
  electric-piano node, so served behaviour doesn't change, but keys.* numbers in the
  ablation mix the MIDI change with this source change.
- **Clean models are calibrated on clean data:** T is fit on the commercially licensed
  OpenMIC-train clips only, and the all-clips T is recorded alongside. The sidecar's
  licence text follows the checkpoint's `commercial_clean` flag.
- **Pipeline:** 6,000 songs (30 s to generate). A 20-clip smoke build gave 20/20
  `commercial_clean` labels, and `commercial_only` loading is non-empty. The 10k render
  starts after the GPU run.

**F6. The licence cost, measured.** The clean model is the v7sg recipe (gain ±12 dB,
seed 0, 40 epochs) on 10k renders of procedural MIDI with `--commercial-only`: 7,692 train
clips vs 8,216 for v7s, since the group-hash splits differ.

| test | clean (procedural) | v7sg (Lakh) | v7s (served this morning) |
|---|---|---|---|
| MoisesDB pooled leaf mAP | **0.471** | 0.490 | 0.408 |
| synthetic test, Lakh compositions | 0.711 | 0.846 | – |
| synthetic test, procedural compositions | 0.879 | – | – |

- **On real music the licence cost is small:** −0.02 mAP like for like. It also beats the
  research-only model served this morning (0.408), but that gap comes from the gain fix,
  not from being licence-clean.
- **Where it loses (MoisesDB / OpenMIC, paired CIs):**
  - drum machine −0.19 [−0.36, −0.02];
  - electric piano −0.10 [−0.24, −0.03], confounded: jRhodes3d, 1,070 Rhodes stems, is
    gone;
  - organ −0.12 (OpenMIC);
  - saxophone −0.19 [−0.25, −0.14] (OpenMIC) and woodwinds −0.55 (MoisesDB, 14 positives).
    Random-walk melodies don't teach real wind phrasing.
- **Where it wins:** violin, cello, clarinet and flute on OpenMIC, +0.05 to +0.09. These
  are untrained classes, so this is a side effect, not skill.
- **Synthetic tests overstate the cost:** the composition shift costs 0.14 on Lakh-composed
  test clips but only 0.02 on real music, so in-domain synthetic tests are the wrong
  judge.
- **Suppression rule on the clean model:** pad (0.07), organ (0.07) and electric piano
  (0.01) would be suppressed.
- **Licence chain checked in a scratch export:** the sidecar says commercial-clean, and T
  is fit on the 1,461 commercially licensed OpenMIC clips. T = 3.75, against 4.55 on all
  clips and 2.03 for the Lakh model. Procedural training makes the model more
  overconfident on real music, and the small clean calibration set shifts T by about 0.8.
- **Not served. Switching is Bradley's call, and it wouldn't make the app clean:**
  - the routing constants are tuned for v7sg, so pad would go back to suppressed and
    presence would be re-checked;
  - the PANNs calibration is still fit on mixed-licence OpenMIC (F7);
  - the PANNs checkpoint licence is still marked "verify" in SYSTEMS_DESIGN §4.

  It would make *our* model clean, not the whole app.

**F7. PANNs calibration on clean data only.** I refit on the commercially licensed OpenMIC
clips (`panns-calibrate --licence commercial`). On MoisesDB with the shipped stem rule:
- false detections rise from 471 to 548;
- guitar recall@0.3 falls from 0.82 to 0.73;
- piano rises from 0.31 to 0.45;
- voice and drums are unchanged.

The drums fit is degenerate: only 56 positives make the classes separable, so b hits its
+50 bound. It would need regularisation before shipping. **The all-clips fit stays

**F5. UI provenance** now shows each stage's version (e.g. `panns-sed cnn14+platt@b8a3…`)

## Honesty caveats

- **These test sets no longer judge the routing independently.** I chose routing and
  suppression *after* seeing MoisesDB and OpenMIC test numbers. The golden set is the
  clean test.
- **The stem rule was also picked on MoisesDB.** It's a rule I can justify up front
  ("Demucs stems are only meaningful for their target"), but it was compared on the same
  test windows. The golden set is the clean test.
- **The PANNs calibration fit a different statistic.** It was fit on p95 over 10 s clips,
  but the app takes p95 over a whole song. That's the same unevaluated song-level gap, now
  for PANNs too.
- **Speech counts as voice.** `AUDIOSET_MAP` sends AudioSet "Speech" to voice, and voice's
  calibration is steep (a = 1.58, b = +5.6), so spoken passages will likely show as voice.
  Not fixed.
- **Song-level p95 is unevaluated.** p95 over windows hasn't been evaluated at song level.
  An instrument playing a single 10 s solo can be discounted.
- **Leaf confidences are uncalibrated** (`calibrated: false`, always "?") until the golden
  set gives real leaf labels.
- **One test song** (22 kHz mono, CC): it's a sanity check, not evidence.
